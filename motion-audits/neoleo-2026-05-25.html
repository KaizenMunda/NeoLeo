Primary: Jakub Krehel — Production Polish

NeoLeo's landing page demonstrates solid foundational motion design with Framer Motion staggered entrances and smooth card interactions. However, critical accessibility gaps break the experience for users who prefer reduced motion, and static text animations violate the principle of invisible motion — they announce themselves rather than serving a functional purpose. The implementation is production-ready at its core but needs two focused fixes: respecting user preferences universally, and applying a critical filter to conditional renders that currently lack animation. With these corrections and selective enhancements (blur on enters, subtle exits), this could be a polished, professional landing experience that respects both performance and accessibility.

Critical Issues

🔴 Critical

Framer Motion Animations Ignore prefers-reduced-motion

Hero.jsx's Framer Motion animations do not respect the prefers-reduced-motion: reduce media query. Users who have enabled reduced motion in their OS settings (due to vestibular sensitivity or other motion-related disabilities) will still see the 0.8s fade-in animations on every page load. This is an accessibility violation under WCAG 2.1 criterion 2.3.3.

Impact: Users with motion sensitivity experience discomfort. Current Framer Motion v11 does not natively respond to this media query; you must wrap animations with a conditional check.

🔴 Critical

Looping Particle Animation Has No Pause Control

ParticleBackground.jsx uses Canvas requestAnimationFrame to create a continuous looping particle animation with no pause or stop control. Per WCAG 2.1 criterion 2.2.2, any animation that runs for more than 3 seconds must either (a) auto-pause after 3 seconds, (b) allow the user to pause/resume, or (c) be central to the information being presented. The particle background is purely decorative and cannot be paused.

Impact: Users with vestibular or photosensitivity disorders experience discomfort or distraction. The animation runs continuously across all pages without escape.

Important Issues

🟡 Important

Stagger Entrance on Static Text (Heading, Subtitle, Description)

The hero section's text (NEO/LEO heading, "Bold Vision · Precise Execution" subtitle, and body copy) all receive staggered fade-in animations with 0.8s duration and 0.2s delays between children. This is the anti-pattern: motion-on-mount-for-static-content. Polished production UIs let text appear instantly and animate interactive elements only. When text announces itself with motion, the UI feels self-aware rather than invisible.

Jakub's test: Remove the animation. Do users feel something is missing? For text, the answer is no — they just want to read. The animation is announcing itself, not serving function.

🟡 Important

Hero Staggered Items Lack Exit Animations

The hero container's staggered items (.hero-title, .hero-subtitle, .hero-description, .hero-buttons) all have initial={{ opacity: 0, y: 20 }} and animate={{ opacity: 1, y: 0 }}, but no exit animation. When users navigate away or the component unmounts, the items vanish instantly. Per Jakub's philosophy, exits should be subtler than enters (smaller movement, same blur).

Impact: Page transitions feel abrupt. Without exit motion, the visual narrative breaks.

🟡 Important

Button and Hero Entrances Missing Blur for Polish

Current enter animations use opacity + translateY but omit filter: blur(). Jakub's signature technique is opacity + translateY + blur — the blur creates a "materializing" effect that feels more physical than fade alone (the element appears to come into focus, not just fade in). Adding blur to the hero buttons and the video visual entrance would elevate the polish without increasing duration.

Recommendation: Enhance with filter: blur(4px) on initial, animate to blur(0px). Existing durations (0.8s) accommodate this without feeling sluggish.

Issues to Address

  • ⚠️ Hero entrance durations (800ms) exceed Emil's 300ms productivity guideline — acceptable for a marketing/landing page (Jakub/Jhey territory), but borderline slow. Consider 500ms as compromise if performance perception matters.
  • ⚠️ Particle animation runs continuously without frequency gate. Even if pause control is added (critical fix), the default should be off for users on slower devices.

Opportunities

  • 💡 Apply Emil's frequency gate to the particle background — disable by default on mobile where battery and CPU matter ParticleBackground.jsx
  • 💡 For high-frequency card hovers (solutions, case studies, career listings), consider removing the 8px lift and keeping only the glow shadow. After 20+ interactions, the lift becomes tiresome.

Through Emil's lens: Emil's strength is knowing when NOT to animate. The hero entrance animations are the only place where his speed preference (under 300ms) is stretched. For a landing page where users aren't task-driven, this is acceptable — they're not scrolling through dozens of interactions per minute. The critical issue is the particle background: it animates continuously without pause and doesn't respect user preferences, violating Emil's principle of purposeful motion.
